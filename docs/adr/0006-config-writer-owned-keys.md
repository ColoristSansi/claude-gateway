# 客户端配置写入用「接管键清单 + 原子替换」，冲突只看接管键

客户端配置文件是**别人的文件**：用户会手写注释、别的工具会往里加自己的段（本机 Store 版 Codex 桌面应用持续往 `~/.codex/config.toml` 写 `[desktop]` / `[marketplaces.*]` / `[plugins.*]`，共 10 段插件表）、客户端自己也会改它。所以「保留用户的改动」必须先回答「哪些键是我的」；写坏 Desktop 的 3P 配置就是登录态与配置双损。现有最小实现（`.scratch/model-gateway/prototype/desktop-3p.ps1`）三处被否决：`gateway` 对自己那份 profile 整份重建（非接管键全丢，`:57-70`）、`standard` 不维护 `_meta.json`（entries/appliedId 残留，`:87-104`）、`restore` 删整个 configLibrary 再拷回（会把 app 后来建的 profile 一起毁掉，`:106-112`），且一律 `Set-Content` 原地写（`:48-49`），无原子替换、无并发或外部改动检测。

决定：

1. **显式接管键清单**（每个「客户端 × 文件」一份）+ 按格式保序改写；清单外的键原样保留；**解析失败即停**，绝不退回空文档重写。
2. **唯一真相在 SQLite** `client_config_state`：上次由网关写入的接管键值、时间、备份路径、首写时文件是否存在。冲突检测、幂等、还原都读它，不另设状态文件。
3. **写入 = 同目录临时文件 + fsync + 原子替换**（Windows `ReplaceFileW`，遇 `NotFound` / `ERROR_NOT_SUPPORTED` 退 `fs::rename`，最多 3 轮）；失败即删临时文件；不做父目录 fsync。被占用/权限失败退避重试 3 次后报错并给出文件路径、备份路径与占用提示。
4. **冲突只看接管键**：写前比对「接管键现值」与「记录的上次写入值」；非接管键与别的程序写的段变化**不算冲突**。冲突 = 放弃本次 + 提示，不覆盖、不自动合并；记录缺失按首次接管处理（备份后写 + 提示）。
5. **接管键以网关为准**（覆盖用户手改），非接管键保留——票 19 断言③的「用户手改过的字段」按非接管键理解。
6. **幂等 = 语义相同就不写**（连 mtime 都不变）；要写则沿用目标文件原有的缩进、行尾、BOM，并保证连续两次结果字节相同。
7. **还原默认摘键**（含指针性条目：Desktop 还要摘 `_meta.json` 的 entries、`appliedId` 回退，不动别的 profile）；**整份回滚**是显式第二选项，仅当文件自上次网关写入后未被外部改过；网关当初新建、且现在只剩网关内容的文件整个删掉。
8. **多文件按依赖顺序逐个原子替换**（先被引用者、后指针），中途失败报错并列出已改文件；**不做跨文件 pending 事务与启动补完**。单实例互斥量 + 每文件一把锁，不做跨进程锁文件。

理由：把「我拥有哪些键」显式写下来，才让「保留用户改动、幂等、可还原」这三件事有判据，而不是靠每次推测目标状态；冲突只看接管键，是因为别的程序写它自己的段是常态，整份哈希会常驻误报，而冲突的代价（放弃一次写入）远小于误覆盖。

**Status**: accepted（2026-10-15，由 [票 28](../../.scratch/model-gateway/issues/28-grilling-config-writer-transactionality.md) 四轮弹窗定案，共 21 条；规则同步进 spec §8 / §8.4）

**Considered Options**:

- **整文件重建**（现有 ps1 的 `gateway` 模式）：把用户与别的工具写的键一起抹掉。否决。
- **整目录快照回滚**（现有 ps1 的 `restore`）：回到首写状态，顺带毁掉客户端后来创建的其他 profile。否决，改为摘键 + 可选的单文件回滚。
- **先备份再原地截断写**：崩溃窗口里目标文件可能是半截。否决。
- **冲突用整份文件内容哈希**：Codex 的 `config.toml` 有别的写入方，会常驻误报。否决。
- **冲突后自动三方合并**：合并语义难定义、难断言，收益不抵出错面。否决。
- **移植 cc-switch 的跨文件 pending 事务 + 启动补完**（`vendor/cc-switch/src-tauri/src/mode/operation.rs:121-194`）：能力更强，但多一整套恢复引擎要维护与测试；本项目的写入方只有一个进程。否决。
- **跨进程锁文件**（如 `<目标文件>.lock` + 陈旧锁超时）：单实例互斥量已保证只有一个写入方，冲突检测兜底。否决。
- **备份只留首写一份 / 与目标文件同目录**：前者没有中间回退点，后者弄脏客户端目录。否决。
- **状态放数据目录 JSON**（cc-switch 的 `live-state.json` 形态）：与 SQLite 双源，要额外防不一致。否决。

**Consequences**: 每个客户端文件都要维护一份接管键清单——Codex 的顶层清单（`model_provider` / `model_providers.<id>` / `model_catalog_json`）仍待落进 spec，模型目录指针那一半归 [票 31](../../.scratch/model-gateway/issues/31-grilling-codex-model-catalog.md)。真写入会把 TOML 里用户自己的注释洗掉（无变化时不写，所以平时不碰）。不做 pending 事务意味着多文件写入中途失败的收尾靠报错信息里列出的已改文件，而非自动补完。备份布局（`%APPDATA%\com.claudegateway.desktop\backups\<客户端>\`，首写快照常驻 + 滚动 5 份/90 天）与「卸载默认摘键」也由此固定。现有 `desktop-3p.ps1` 的三处行为需按本 ADR 重做，属实现面。
