# 配置写入引擎的事务性

Type: grilling
Status: resolved
Blocked by: —

## Question

写客户端配置文件时，并发写、写到一半崩溃、用户手工改过之后的重写，分别怎么办？

## 为什么现在问

票 19 第 10 条已经定了**断言什么**（幂等、首写备份可还原、用户手改的字段不被抹掉、还原后接近原状，且测试只在临时目录里跑），但没定**什么行为能让那些断言成立**。写入引擎是全项目风险最高的一块——Desktop 的 3P 配置写坏就是登录态与配置双损（票 15 已实测 3P/1P 登录态隔离）。

## 需要定下来的

1. 原子性：临时文件 + 原子替换（Windows 上是 `ReplaceFile` / `MoveFileEx`），还是先备份再原地写；崩溃窗口里留下什么。
2. 并发：同进程内的写串行化是否够；用户手动开着编辑器改文件、应用同时重写的冲突检测（mtime / 内容哈希）与处理（放弃这一次、还是提示）。
3. 「只改关键字段」的边界：用户手工改过被网关接管的字段之后，重写是覆盖还是保留；票 03 抄的 cc-switch 做法在这里的适用边界。
4. 幂等的判据：是「跑两次字节相同」还是「语义相同即可」（`meta.json` / 顺序 / 换行差异算不算）。
5. 还原（restore）的语义：恢复到首写备份的快照，还是只摘掉网关写入的键；备份保留几份、放哪、什么时候清理。

## Answer

（2026-10-15 与用户四轮弹窗定案，共 21 条；每条都由用户逐条选择，无自答。）

### 0. 现状基线（本次核对过的既有实现与参考实现）

- 现有最小引擎 `.scratch/model-gateway/prototype/desktop-3p.ps1` 三处行为被本票推翻：`gateway` 对自己那份 profile **整份重建**（`:57-70`，文件里原有的非接管键全丢）、`standard` **不维护 `_meta.json`**（`:87-104`，entries/appliedId 残留）、`restore` **删整个 configLibrary 再拷回备份**（`:106-112`，会把 app 后来创建的其他 profile 一起毁掉）；写入一律 `ConvertTo-Json | Set-Content -Encoding utf8` 原地写（`:48-49`），无原子替换、无并发或外部改动检测。
- 参考实现 cc-switch 的 `live/` 引擎（MIT）已核到源码：分层 floor/project/patch，JSON 走 `preserve_order` + `shift_remove`，写时沿用原缩进/行尾/BOM（`.scratch/model-gateway/vendor/cc-switch/src-tauri/src/live/patch/json.rs:119-137`）；原子替换 `stage_write` = 同目录 `create_new` 临时文件 + `ReplaceFileW`、遇 `NotFound`/`ERROR_NOT_SUPPORTED` 退 `fs::rename`（`src/config.rs:503,616-641`）；首写备份每文件一次、marker 在即返回（`src/live/engine.rs:158-184`）；跨文件 pending 事务与启动补完在 `src/mode/operation.rs:121-194`。调研既有建议见 `research/similar-gateways.md:319-328`（floor 思路 + 事务回滚）、`:139-140`（显式建模「我拥有哪些键」、乐观并发写进文档、失败方向保留未知键）。

### 1. 引擎骨架：显式接管键清单 + 保序改写（票内第 3 条的上半）

1. 每个「客户端 × 文件」声明一份**接管键清单**（floor）。写入只动清单内的键；清单外的一切（用户自加键、别的工具写的键、Codex 的 `[desktop]` / `[marketplaces.*]` / `[plugins.*]` 段）**原样保留**。
2. **按格式保序改写**：JSON 保键序、删除用「移位删除」语义；TOML 保序。不整文件重建。
3. **解析失败即停**：目标文件解析不过或形状不对时，什么都不写、报错并给出行列位置，绝不退回空文档重写。
4. 唯一真相在 SQLite：新增/明确 `client_config_state` 记「某客户端某文件上次由网关写入的接管键值 + 时间 + 备份路径 + 首写时文件是否存在」。冲突检测、幂等判据、还原都读它。不另设数据目录 JSON 状态文件（避免双源不一致）。

### 2. 原子性（票内第 1 条）

1. **临时文件 + 原子替换**：同目录写 `create_new` 临时文件 → **fsync 文件** → 原子替换。Windows 用 `ReplaceFileW`，遇 `NotFound` / `ERROR_NOT_SUPPORTED` 退 `fs::rename`，最多 3 轮。不做父目录 fsync。
2. 替换失败即删临时文件（**不做前滚**，因为本票不做跨文件事务，见第 7 条）。
3. **写失败重试**：文件被占用 / 权限不足 / 只读 → 退避重试 3 次（~200ms 间隔）；仍失败则报错，并直接给出目标文件路径、备份路径与「可能有客户端正占用该文件」的提示。

### 3. 并发与外部改动（票内第 2 条）

1. **单实例**：应用启动用命名互斥量，第二个实例唤起已有窗口 → 「同进程写入串行化」成立（每个文件一把锁/一个写队列）。**不做跨进程锁文件**；真出现第二个写入方时由冲突检测兜底。
2. **冲突判据只针对接管键**：写前比对「接管键的现值」与「SQLite 里记录的上次写入值」；**非接管键、以及别的程序写它自己的段，一律不算冲突**（Codex 桌面应用会持续写 `[desktop]` 等段，整份文件哈希会常驻误报）。
3. **冲突处理 = 放弃本次 + 提示**，不覆盖、不自动合并。界面表现归票 17 的卡片状态（相当于「值不匹配」态）。
4. **状态记录缺失（首次运行 / 数据库被清 / 换机 / 用户拷来数据目录）→ 按首次接管处理**：先备份、再写、并提示一句。无记录不等于有外部改动。

### 4. 「只改关键字段」的边界（票内第 3 条的下半）

1. **接管键以网关为准**（用户手改接管键会被覆盖），非接管键保留。
   **对票 19 第 10 条断言③ 的明确**：那句话里的「用户手改过的字段」按**非接管键**理解——票 30 写这条断言时只改非接管键，否则断言与本条冲突。已在票 19 追加一行说明。
2. **接管键已被别人写过**（例如 cc-switch 写的 `model_catalog_json`）：先把它写进首写快照，再覆盖并告知用户。「接管」就是接管；Codex 目录与第三方目录并存的具体规则仍归[票 31](31-grilling-codex-model-catalog.md)。
3. **真写入时接受「解析后重序列化」**：TOML 里用户自己写的注释会丢（无变化时压根不写文件，所以平时不会碰；首次接管时界面说明一次）。但缩进、行尾（CRLF）、BOM 有无**沿用目标文件**。

### 5. 幂等判据（票内第 4 条）

1. **语义判据优先**：解析后接管键值与目标一致 → **完全不写文件，连 mtime 都不变**。缩进、键序、换行的差异不构成「变化」。
2. 需要真写入时，写入结果稳定：连续两次执行后文件字节相同（票 19 断言①因此仍成立）。
3. 票 30 的对应断言：① 连续两次运行后字节相同；② 无变化时 mtime 不变；③ 非接管键在写入前后不变。

### 6. 还原与备份（票内第 5 条）

1. **默认还原 = 摘键**：只删网关接管键。Claude Desktop 上还包括：从 `_meta.json` 的 `entries` 摘掉网关 profile 条目，`appliedId` 指向网关时回退；**不动别的 profile**（推翻现有 `restore` 的整目录替换）。
2. **可选整份回滚**：从首写快照恢复该文件；前提是该文件自上次网关写入后**未被外部改过**（用第 3 条的同一套判据），被改过则拒绝并提示。
3. **网关新建的文件**：首写时记下「原先不存在」；还原时若该文件里只剩网关写的内容（无用户自加内容）→ **删除整个文件**，否则只摘键保留。
4. **备份位置与保留**：`%APPDATA%\com.claudegateway.desktop\backups\<客户端>\<文件名>.<yyyyMMdd-HHmmss>`。**首写快照常驻不清理**；滚动备份保留最近 5 份、超过 90 天清理。首写时文件不存在只写 marker，**不造空备份**。
5. **卸载时的还原走摘键**（票 18 的「还原客户端配置」= 本条默认动作），与运行时默认一致。

### 7. 多文件写入的顺序（票内第 1、2 条之间）

一次切换要改多个文件时，按**依赖顺序逐个原子替换**：先写被引用者，再写指针（Codex：目录文件 → `config.toml`；Claude Desktop：profile → `_meta.json`），保证任一时刻不存在悬空指针。中途失败即报错并列出已改动的文件。**不做跨文件 pending 事务与启动补完**（不移植 cc-switch `mode/operation.rs` 那套）。

### 8. 写入历史

每次写入/还原记一条 **SQLite 记录 + 元数据级日志**（沿用票 11 的日志与 7 天保留）。不新做「历史」页面，日志页可见即可。

### 9. 术语与 ADR

新增术语已写入 `GLOSSARY.md`：**接管键**、**首写快照**、**摘键还原**、**整份回滚**、**外部改动（漂移）**。spec §8 的写入引擎规则按本票改写，并新增 §8.4。

**ADR-0006**：本票满足 ADR 三判据（难逆、无上下文会困惑、真取舍），已由用户确认归档为 [`docs/adr/0006-config-writer-owned-keys.md`](../../../docs/adr/0006-config-writer-owned-keys.md)（与票 23→0004、票 19→0005 一致）。

### 10. 原型欠账的归属（2026-10-15 用户定）

第 0 节列出的那些行为差（`desktop-3p.ps1` 的 profile 整份重建、`standard` 不维护 `_meta.json`、`restore` 整目录替换，以及原子替换/冲突检测/状态记录/滚动备份/参数化根目录等尚未实现的能力）**不开票**，归到「把原型换成正牌应用」那一实现阶段。因此[票 30](30-task-build-regression-suite.md) 第 8 格（写入引擎自身的断言）在引擎落地前只能挂着，[票 19](19-grilling-test-strategy.md) 第 10 条里「把 `desktop-3p.ps1` 参数化」那个载体也随之作废（行为以本票为准）。地图的 **Out of scope** 已同步记一条。
