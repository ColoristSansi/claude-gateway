# 模型自动发现的失败与空结果怎么降级

Type: grilling
Status: resolved
Blocked by: —

## Question

「拉模型」失败的每一支，界面与数据分别怎么办？

拉取时机与缓存已经定了（[票 23](23-design-provider-table-granularity.md)：拉模型时抓一次存库、可手动重拉、请求期不实时查）。本票只定**失败与空结果**：

1. **单条 wire 反查不到**：上游 `/v1/models` 报的 `supported_endpoints` 是路径，按 `pathTemplates` 反查成 wire；查不到就忽略并记一条警告（票 23 已定）。这条警告在界面上怎么呈现——上游卡片上的提示、拉取结果里的一行、还是只进日志？
2. **整个端点不可用**：千问的 Anthropic 面没有 `/v1/models`（必然 404，票 02）。这时是「这个面上没有模型」还是「拉取失败」？两者的文案与后续动作（能否手填）该怎么区分？
3. **拉取整体失败**（网络断、凭据错、超时）：报错之后用户能不能直接手工新增目录条目（票 23 允许手工新增，来源标 `manual` 且锁定），入口放在哪一步？
4. **空结果**（200 但零条模型）：有没有「确实一个都没有」这种情况、还是要当成失败处理？
5. **待探明**：opencode 带凭据的模型清单 **19 条**、不带凭据 **85 条**（票 23 留的尾巴）。差异原因会影响「默认勾选哪一份」——是权限过滤、还是两份不同的清单？本票需要把它探明或明确降级为「默认勾选带凭据的那份」。

## 背景

- 已解析：[票 02](02-research-provider-apis.md)（四家上游的端点点位与 `/v1/models` 的有无）、[票 23](23-design-provider-table-granularity.md)（目录表结构、`supported_wires` 三值、来源优先级 `manual` > `upstream` > `doc` > 未声明、拉取时机）、[票 17](17-grilling-ui-information-architecture.md)（上游四步向导：选供应商与拉模型可跳过、自检强制）。
- 结论要回写 spec §6 与 §10；界面新增的提示若要改动票 17 定的信息架构，在那张票的结论上追加说明。

## Answer（2026-10-15，四轮弹窗 + 一个调研子代理）

**九条定案**：

1. **wire 反查警告的呈现**：拉取结果里内联一行（上游报的路径 + 我们期望的路径），并存进上游记录的「上次拉取警告」→ 上游卡片与列表显示角标；**下次成功拉取时自动清除**。不阻断保存，也**不进概览「最近错误」**（那是请求错误的地盘）。
2. **「不提供模型发现」与「拉取失败」的判据**：**404/405 = 该面上没有模型发现**——软提示「该上游不提供模型发现，请手填模型 ID」+ 手填入口，**不算错误、卡片不报红**；**其他非 2xx（401/403/429/5xx）/ 超时 / 断网 = 拉取失败**，走失败提示。`noModelsEndpoint` quirk 的含义因此收窄为「不必尝试」，通用 404/405 规则兜住没声明过的上游。
3. **整体失败后的手工新增入口**：失败提示里**直接给「手工添加模型」按钮**，在向导同一页内联新增行（条目按 `manual` 锁定）。上游**仍可保存**——票 17 本就允许拉模型跳过、只强制自检。
4. **200 但零条**：按「确实没有可发现的模型」处理，与第 2 条同一支（软提示 + 手填入口），**不报错、不落成失败记录**。
5. **重拉失败保留旧条目**：只提示「沿用上次结果（时间）」，**只有成功拉取才覆盖 `upstream` 来源的条目**（`manual` 锁定条目本来就不被覆盖）。一次网络抖动不清库。
6. **拉取凭据**：用上游 `default` 凭据；没有 `default` 时只有一份就用它，多份则在拉取这一步给下拉选。**不为每个 wire 面重复拉**（`/v1/models` 不属于任何一个 wire）。
7. **不算「未就绪」**：拉取失败与 wire 反查警告**不计入**侧栏「未通过自检的上游数」，也不影响概览三步就绪——判据只看自检（票 17）。
8. **opencode 两份清单**：**只拉带凭据那份，不再做匿名拉取**。票 23 的「两份合并」策略就此收窄为：只在带凭据拉取得到 404/空结果时才退匿名拉取；**没有凭据就不拉**，提示先填 key 或手填模型 ID。
9. **超时与重试**：拉取 **20 秒超时**，超时算失败；**不自动重试**——401/403/429/404 立即返回，5xx/超时也只报一次失败，失败提示里给「重试」按钮由用户点。与票 26「不给上游转发加统一超时」不冲突：这是网关自己去拉一次清单，不是转发用户请求。

**事实（调研子代理实测，2026-10-15；key 全程掩码）**：

| 端点 | 带 `Authorization: Bearer` | 不带 |
| --- | --- | --- |
| opencode Console `GET /inference/v1/models` | 200 / **19**（1681 B） | 200 / **85**（7118 B） |
| opencode Go `GET /inference/go/v1/models` | 200 / **37**（3090 B） | 200 / **37**（字节完全相同） |
| opencode `/zen/go/v1/models`（= 本机 `OPENCODE_BASE_URL`） | 200 / **37** | 200 / **37** |

- **19/85 的差异原因是权限过滤，不是两份清单**：auth19 是 anon85 的**严格子集且顺序原位保留**（前 11 条逐条相同），两份条目字段集合完全相同（只有 `id` / `object` / `created` / `owned_by`，**无任何权限元数据**），顶层无多余字段，`created` 随请求时刻递增（所以「两份 created 差 13 秒」不能当静态清单的证据）。**一个全量后端目录，带 key 按该 key / 工作区的启用集原位过滤。**
- **可见 ≠ 可调用（决定性）**：只在无凭据那份里的 66 条，带有效 key 调用**一律 403 `Model access is disabled`**（Chat / Anthropic / Gemini 三协议一致）；带凭据 19 条里的模型真能 200（`mistral-large-4`、`qwen3.8-flash`、`claude-haiku-5-5`、`claude-sonnet-5-5` 实测）。
- **anon85 不是官方文档目录的拷贝**：含内部条目 `test`、`claude-opus-5-5-backup`，缺文档里的 `exo-free` 等 → 它是后端原始目录，不是策展清单。66 条里**无一条以 `-free` 结尾**（所有 `*-free` 两份都有）。
- **Go 面与凭据无关**：`/inference/go/v1` 与 `/zen/go/v1` 字节一致（同一服务），37 条带不带 key 一样；**19/85 只是 Console 面的现象**。`x-opencode-session` 只影响 go 的 chat（无它 400 `MissingSessionID`），列表端点从不要求它。
- **免费层另有独立闸门**：auth19 里的 `-free` 模型带 key 调 Chat 面 → 403 `FreeTierError: OpenCode's free tier can only be used from within OpenCode`（加 UA + session 依旧 403）。
- 不确定处：19 = 「工作区启用集」来自官方文档 + 403 行为，看不到 console 开关状态；「该 key 所属计划的可用集」是等价说法。换 key 是否也 19、19 是否随时间恒定，未验证。

**回写**：spec §6（拉取规则与失败降级）、§9（`upstreams` 加「上次拉取时间 / 结果 / 警告」）、§10（上游列表列与向导项目）；GLOSSARY 加「模型发现」；[票 17](17-grilling-ui-information-architecture.md) 追加一节说明相对其 §2 的改动。**票 23 的遗留尾巴（19/85）就此结清**，其「合并」策略由本票第 8 条收窄。**本票不留新票**，无新雾。
